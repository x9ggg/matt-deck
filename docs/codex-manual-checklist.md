# Codex 桌面应用手动检查清单

Deck 在 Codex 桌面应用上的有些行为，两个测试接缝（Deck 服务的工具接口、假宿主下的页面）都覆盖不到，只能在真实的桌面应用里照着做一遍。清单的范围来自规格 #64 的“Testing Decisions”，以及 #64 下各张 Task 关闭时留下的“只能在真实桌面应用里核对的”。

每一条是“做”和“应看到”（2.2、3.7 除外，它们只指向 1.5 里做过的地方）；一条里有几个“做”的，每个“做”后面都跟着它的“应看到”。一条“应看到”里，从 **要核对** 起到这条的末尾，都是还没有在真实的桌面应用里看到过的结果：照做之后写下实际看到的，不符时开 Task。排在标记前面的（整条没有标记的就是整条），是探针记录（`docs/research/probes`）或某张 Task 的关闭评论里已经看到过的，再走一遍是为了发现宿主升级后的变化，出处写在括号里。Pane 自己画的字（按钮、提示的措辞）以假宿主下的页面测试为准，install 和 uninstall 的输出与写出的文件不经过宿主，以 `tests/codex-install.test.ts` 为准，不标 **要核对**、不写出处（1.1、1.6 和第 10 节里的就是）；清单只在它们和宿主有关时才写出来。收拾和换回原样的步骤（第 5 节最后、第 9 节第一步、8.9、第 10 节最后几步、第 11 节），“应看到”只确认收拾好了，也不标、不写出处，第 11 节里宿主的信任记录除外。

两次探针用的是桌面版 26.1117.41037，自带 `codex-cli 0.171.0-alpha.13`（规格 #64 的 Further Notes）；#68 用的是同一个桌面版（#68 的关闭评论）。每次走清单先记下桌面应用的版本、Deck 检出的提交号，再逐条写结果：成立、不成立（写看到了什么）、没做（写为什么）。

## 准备

- 清单会动到整台机器：install 和 uninstall 改的是用户全局的文件，对这台机器上所有 Codex 项目生效；清单里多次退出、重启桌面应用，每次都会让所有 Codex 会话正在进行的回合断掉；3.9、8.6、8.8 改 `/etc/hosts`（要 `sudo`）时，所有程序到 `api.github.com` 的连接都挂住；8.8 的旁白开着时读的是整个屏幕，也会接走一部分按键。走之前让别的 Codex 会话停在回合之间。照清单走的若是 agent，它不能跑在 Codex 桌面应用里（退出应用就切断了它自己），要跑在终端里，例如 Claude Code；它这时也别用 `gh`、别连 GitHub，直到 `/etc/hosts` 改回；它没有 `sudo` 的话，这三处里改 `/etc/hosts` 的部分记为没做。
- 一份专门为这份清单 `git clone` 的 Deck 检出，下面的 `<检出>` 都指它。别的 Session 不在里面工作（照清单走的 agent 自己的工作目录也不在里面），也不要用平常用的那份检出：1.6 要把它挪走，平常用的那份检出挪走之后，它的各个 worktree 里指回它的 gitdir 链接全断，在里面工作的会话也没了目录；6.2 换上、8.6 和 8.7 也用的页面副本也落在这一份上。Node 和 `gh` 满足 README 的前置条件，`gh` 已登录。
- 先退出桌面应用，到 1.2 再打开。应用开着时卸载再装，重启之前在任何 Configured Project 里发出一条消息，内存里旧的钩子就会照常调用工具、记下时间，1.2 就看不到橙色提示（#110）。

- 6.2、8.6 和 8.7 用一份记日志的页面副本：直接改专门检出里的 `plugin/codex/pane.html`，不提交。6.2 开始前换上、重启桌面应用，一直留到第 8 节做完；第 9 节之前运行 `git -C <检出> checkout plugin/codex/pane.html` 换回原来的页面，再重启。不要在第 8 节中间换：重启会让那里备好的乙的 Occupancy 变成 Orphaned。改法照页面现有的结构：在 `<body>` 末尾的 `<script>` 前面加一个 `<pre id="probe-log" style="color:var(--ink);white-space:pre-wrap"></pre>`（它在 `.dk-pane` 外面，不写颜色的话深色下是黑字，不写换行的话长行被截）；在 `<script>` 里那个 async 函数的开头定义一个 `log`，把一行 `new Date().toISOString()`、事件和当时的 `document.activeElement` 写进 `probe-log` 末尾，同时 `console.log` 一份；元素写成标签名加它的文字，文字截到前 15 个字左右，如 `BUTTON 取消`；`BODY`、`HTML` 只写标签名：它们的文字是整页的内容，前 15 个字多半是空白，写出来没有意义（载入时、点“我现在该做什么”之后焦点落回页面时、之后每 2 秒一次的 `deck_recommendation` 都会写这样一行）；`null` 照写。每行同时记下 `document.hasFocus()`（8.6、8.7 用）。在 `callTool` 的第一行 `log(name)`，60 秒一次的读取、“刷新”和 `deck_recommendation` 都经过它；在 `log` 定义之后立刻记一次 `document.visibilityState`，再 `document.addEventListener('visibilitychange', () => log(document.visibilityState))`；再加 `document.addEventListener('focusout', event => { log(...); setTimeout(() => log('focusout 之后'), 0) }, true)`（8.6、8.7 用），第一次记 `event.target` 和 `event.relatedTarget`：派发 `focusout` 时焦点还没落到新元素上，这一行的 `activeElement` 多半是 `BODY` 或 `null`，焦点落到哪里看紧接的“focusout 之后”那一行（8.7 说了什么时候这一行不算数）。再加 `document.addEventListener('focusin', event => log(...), true)`，记 `event.target`；和 `window.addEventListener('focus', () => log('window focus'))`、`window.addEventListener('blur', () => log('window blur'))`（8.6 用：⌘Tab 回到桌面应用时 `focusout` 和 `visibilitychange` 都不一定有，回来时焦点进没进页面看 `window focus` 那一行和随后的 `focusin`）。这几行照样带 `activeElement` 和 `hasFocus`。看日志：在 Pane 里滚到最底下读 `probe-log`，用截屏留下；滚动不点页面，不改焦点。Pane 重画时 `probe-log` 不会被清掉：页面重画的只是 `.dk-pane` 里的几块，`<pre>` 在它外面。**要核对**：宿主会不会重新加载页面：日志从头开始、少了前面的行，就是重新加载过，照实记下。`console.log` 那一份能不能在桌面应用里看到，没有记录看过，看不到就只用 `probe-log`。`document.hasFocus()` 在桌面应用里的表现也没有看过：按浏览器的行为，焦点在页面里时是 `true`，回到宿主的输入框时是 `false`。

## 1. 安装、信任钩子和重启

**1.1 安装的输出**

- 做：运行 `node <检出>/plugin/cli/codex.ts install`。准备里已经退出了桌面应用；别的装了 Deck、开在 Configured Project 里的 Claude Code Session 照 8.9 的说法能退的先退：它们的心跳和 install 争本机状态的写锁，争不到的话 install 忘不掉之前收到的钩子调用，1.2 的橙色提示不出现。
- 应看到：输出逐行说写了 `~/.codex/config.toml`、`~/.agents/skills/matt-deck-configure/SKILL.md`、它旁边的 `agents/openai.yaml`（这里原来就有一份不是 Deck 写的时，说没有改它）、`~/.codex/hooks.json`（原来有这个文件时说备份在 `hooks.json.before-matt-deck`；准备里的 uninstall 留下了备份时，即说“安装前的钩子文件备份留在 … 没有删”的那种，这一行前面还有“之前留下的备份 … 已挪到 …”，挪到的名字是后面加上第一个没被占的编号，如 `hooks.json.before-matt-deck.1`；Deck 之后不再碰这份带编号的，确认内容不再需要后可以自己删）；接着是“接下来两步：在终端里运行一次 codex，在钩子审查里信任 Deck 的钩子；再重启 Codex 桌面应用。之后每个 Session 的标签页菜单里出现 Matt Deck，发出的 $implement 会登记占用。”；倒数第二行写明注册指向哪一份插件；最后一行写明注册里的 `node` 是哪个路径，这个路径没了之后要重新运行一次 install。`config.toml` 里 `[mcp_servers.matt_deck]` 的 `command` 是一个 `node` 的绝对路径，和最后一行写的一字不差。

**1.2 没信任钩子时**

- 做：先不去终端，直接打开桌面应用（准备里已经退出）。在 Configured Project 里新建会话，发一条普通消息，打开 Pane。
- 应看到：Pane 能打开（#68 第 2 步）。**要核对**：抬头和四个标签页之间有一条橙色提示“钩子未生效，开始执行不会登记占用。”，右端是“怎么做”，提示只占一行（#77）。点“怎么做”，下面是三步：在终端里运行一次 `codex`；在钩子审查里信任 Deck 的钩子；重启桌面应用。按钮换成“收起”（假宿主下测过，#77）。
- 依据：没信任的钩子不运行，桌面应用也不提示（`codex-hooks` 探针第一轮、第二轮）。

**1.3 信任之后**

- 做：在终端里、在 Configured Project 的目录里运行一次 `codex`（换个没信任过的目录，会多出一次目录信任），在启动时的 Hooks need review 里信任 Deck 的钩子（`UserPromptSubmit` 上调用 `matt_deck` 的 `deck_prompt_submitted`）；准备里记下 Deck 之后还有别的钩子的话，审查里一并信任它们。不发消息就退出：在 Configured Project 里发出的消息会让钩子记下一次调用，1.5 就看不到提示还在。退出并重新打开桌面应用。先不在 Configured Project 里发消息，接着做 1.4（适用时）和 1.5。
- 应看到：终端里出现钩子审查（`codex-hooks` 探针第二轮）；信任之后 `~/.codex/config.toml` 的 `[hooks.state]` 多一条记录，键由文件路径、事件名和钩子在文件里的位置组成，如探针里的 `hooks.json:user_prompt_submit:0:1`，值是内容的哈希（同上）。照实记下审查列出了哪些钩子。信任之后提示是否消失，在 1.5 的最后一步看。
- 另记下（**要核对**，#74）：这台机器原来没有已信任的钩子时，这一项记为没做；有的话，安装前你已经信任过的钩子，这次审查里有没有再列出来、要不要重新信任。

**3.9 钩子慢的时候**

- 做：只让到 GitHub 的连接挂住，而不是立刻失败；到模型服务的连接不能动，否则回合开始不了。只是断网的话，`gh` 可能立刻报连不上，碰不到钩子的 `timeout: 10`。在 `/etc/hosts` 里加一行 `10.255.255.1 api.github.com`（一个不可路由的地址，连接会一直等着），运行 `sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder` 让它生效，再在终端里运行 `gh api user`，记下（**要核对**）它多久失败；它在 10 秒内就失败的话（例如立刻报连不上），钩子碰不到 `timeout: 10`，删掉那一行、清缓存，这一步记为没做。Deck 读 Task Source 时调用 `gh` 不设超时，8.6、8.8 等 `gh` 失败全靠这里量出的时长：那两处等过这个时长的两倍 `gh` 还没失败的话，先删掉 `/etc/hosts` 里那一行、清缓存，把那一步记为没做。这一行对整台机器上所有连 `api.github.com` 的程序都生效，别的 Session 里的 `gh` 也会挂住，改回之前不要在别处用。离这个会话的 Pane 上一次读取（60 秒一次的读取或“刷新”）超过 15 秒再发：钩子的工具先用 15 秒内读过的 Task Source，不连 GitHub；超过了就必须现读，`gh` 一直挂到失败。所以这种挡法下这个 Task 一定不登记：Deck 自己读 Task Source 失败，吞掉错误、不登记，不论宿主超时后怎么做。发出 `$implement #<编号>`（另一个可执行的 Task），记下从按发送到回合开始用了多久；回合开始后停下它，agent 读 GitHub 也会挂住。最后删掉 `/etc/hosts` 里那一行，再运行一次上面那条清缓存的命令。
- 应看到：**要核对**：从按发送到回合开始用了多久，看钩子里写的 `timeout: 10` 的单位是不是秒；超时后宿主怎么做（对话里有没有报错、回合是否照常开始）（#74）。那个 Task 没登记是 Deck 读 Task Source 失败的结果，说明不了宿主的超时行为，不当作这一步的结果。

## 7. Session 结束、重启桌面应用之后

以 Codex 为宿主时，Deck 服务从它收到的第一次带会话标识的调用起，为这个 Session 每 60 秒写一次心跳，只在 Configured Project 里写；收到 `SIGTERM` 时写下这个 Session 的结束记录再退出。Occupancy 在 Session 有结束记录时，或最后一次心跳超过 3 分钟时，是 Orphaned；同一个 Session 再有调用时恢复为进行中（#75）。下面要核对的是真实的桌面应用什么时候结束和重起 Deck 服务。

这一节用到的每个会话，都先在 Configured Project 里新建，照 3.3 对一个可执行的 Task 点“执行”并发送，刷新后它写“本 Session”，下面说“登记一个 Task”就是指这样做。要在桌面应用之外看 Occupancy，在这个项目的目录里运行 `node <检出>/plugin/cli/main.ts`，读 `occupancies` 里这个 Task 的 `isOrphaned`；它只读，不写心跳。用 Claude Code 打开同一个项目的 Pane 也行，Orphaned 的 Task 在“进行中”里标着 Orphaned。

**7.1 切走和 Session 卸载**

- 做：新建一个会话（下面叫甲），登记一个 Task。切到另一个 Session，过 4 分钟以上，运行一次命令行检查，再切回甲。然后试桌面应用里能让一个会话结束的操作（例如归档会话、删除会话）：每种操作各新建一个会话，登记一个 Task，再对这个会话做这种操作，马上运行一次检查，4 分钟后再运行一次。甲不做这些操作，7.2 和 7.3 要用它。
- 应看到：切走一分钟，这个 Session 的服务进程一直活着（`codex-hooks` 探针，那时测的是探针自己的服务）。**要核对**：切走 4 分钟以上，甲的 Task 的 `isOrphaned` 仍是 `false`；哪种操作会让 Session 卸载（探针没有观察到过 Session 被卸载）。卸载时若服务收到 `SIGTERM` 并写下了结束记录，马上那次检查就是 `true`，Claude Code 的 Pane 里是 Orphaned；若要等 4 分钟那次才是 `true`，说明服务没写下结束记录：可能是先关了输入、收到的不是 `SIGTERM`，或没写完就被结束了。写下是哪一种情况。

**7.2 退出桌面应用**

- 做：回到甲，先运行一次命令行检查，确认甲的 Task 是 `false`，记下甲的 Pane 抬头的 8 位。甲的 Pane 开着时退出桌面应用，10 秒之内再运行一次检查。
- 应看到：应用退出时，Session 的服务进程收到 `SIGTERM`（`codex-hooks` 探针，那时测的是探针自己的服务）。**要核对**：马上那次检查里 `isOrphaned` 已是 `true`。结束记录要在等锁的 2 秒之内写完，Codex 发出 `SIGTERM` 之后多久强行结束进程没有测过；检查要过 3 分钟才是 `true`，就是结束记录没写下。

**7.3 重新打开桌面应用**

- 做：重新打开桌面应用，回到甲，不发消息，运行一次命令行检查。然后从菜单打开 Matt Deck，看抬头的 8 位，再运行一次检查。
- 应看到：对话恢复，标签页没有恢复，那一栏是收起的（`adr6-thread-tab` 探针记的“页面重建”没有写标签页是不是自己回来的，见那里的“和 #68 不同”；标签页自己回来了的话照实记下，不用从菜单打开，后面看的就是它。这时没有“打开 Pane 之前”：回到甲时页面就加载了，加载时读取一次，这次调用带着会话标识，Deck 服务从它起为甲心跳，所以第一次检查是 `false` 是对的，照实记下，下面“仍是 `true`”那项只在标签页没有回来时核对）；从菜单重新打开 Matt Deck，Pane 正常，显示同一个 Session，抬头的 8 位和 7.2 记下的相同，中间不用再发消息（#68 第 6 步：退出时两个 Session 的 Deck 服务进程都结束了，重启后显示的是同一个 Session）。恢复的 Session 起了新的服务进程（`adr6-thread-tab` 探针“重启后回到 A”：宿主恢复 Session 时重新启动了它的 MCP 服务），第一次调用带的是同一个会话标识（#68 第 6 步，抬头的 8 位就是从它来的）。8 位变了的话是标识不同，那个 Task 仍是 Orphaned，照实记下。应用启动时宿主起的短命进程没有收到过工具调用（`codex-hooks` 探针）。**要核对**：打开 Pane 之前那次检查仍是 `true`；打开 Pane 后，那个 Task 第一次显示就在“进行中”，写“本 Session”，再运行检查是 `false`（#75）。
- 做：再退出、重新打开一次，这次不打开 Pane，在甲里发一条普通消息，再运行检查。
- 应看到：**要核对**：经钩子的调用也让它恢复，检查是 `false`。
- 做：在甲里再发一条 `$implement #<编号>`（另一个可执行的 Task），从菜单打开 Pane 看。
- 应看到：**要核对**：钩子在重启后照常运行，Task 登记到“进行中”。

## 8. 接管和释放

这一节要三个被占用的 Task，都在同一个 Configured Project 里：一个是 Orphaned；一个由这个项目里另一个 Codex 会话占用；一个由 Claude Code 的 Session 占用。退出桌面应用会让所有会话的 Deck 服务结束（#68 第 6 步），所以先备好 Orphaned 的那一个：前面各节登记过、之后退出过桌面应用而没再回到那个会话的 Task 就是，命令行检查里 `isOrphaned` 是 `true` 就能用；没有的话，在一个会话里照 3.3 登记一个，退出并重新打开桌面应用，不回那个会话，等检查是 `true`（没写下结束记录时要过 3 分钟）。然后新建一个会话（下面叫乙），照 3.3 登记一个；再用 Claude Code 打开同一个项目的 Pane，对一个可执行的 Task 点执行并发送（前提见准备里 Claude Code 那一条）。最后在同一个项目里再新建一个会话（下面叫丙），发一条普通消息，打开 Pane；下面都在丙的 Pane 里做。8.6 到 8.8 每次打开确认，还要一个别人占用的或 Orphaned 的 Task，前面各节留下的 Orphaned 的就行；8.6 的回车落到“接管”上时、8.7 点“接管”时，都是真的接管一个 Orphaned 的，之后它是丙的，不再拿来打开确认。按钮的规则、确认的位置和措辞照 `docs/codex-tab-layout.md` 的“任务”一节，在假宿主下测过（#76）；这一节核对的是真实桌面应用里的样子。

**8.1 按钮**

- 做：在“任务”的“进行中”里看这三个 Task 的行，再点进各自的详情。
- 应看到：**要核对**：被另一个 Codex 会话占用的写 `进行中 · <8 位>`，被 Claude Code 占用的写 `进行中 · Claude Code <8 位>`，这两行只有“接管”；Orphaned 的写 `Orphaned`，有“接管”和“释放”；详情的返回栏上一样（#76）。

**8.2 确认出现在点的位置**

- 应看到：**要核对**：确认画在点的那个位置（行、详情返回栏下面、卡片、Recommendation 主按钮的位置），列表的其余部分不动，页面不跳；标题是 `#<编号> 正由 Session <8 位> 执行`，说明是“接管会把 Occupancy 转给本 Session。”，下面是“接管”和“取消”（#76）。对被 Claude Code 占用的那个点“接管”，标题是 `#<编号> 正由 Claude Code <8 位> 执行`，带宿主名；对 Orphaned 的，标题是 `#<编号> 的 Session 已结束`（#76）。

- 应看到：**要核对**：不出确认，Task 回到“可执行”（被阻塞的回到“阻塞”）（#76）。释放失败时页面不说原因，只是行原样不动，见 #111；遇到时写下当时的情况。

**8.6 页面调用 `focus()` 会不会抢走输入框的焦点**

- 做：先把光标放在 Codex 的输入框里，再在 Pane 上点“接管”打开确认，然后马上点回输入框，先不打字，等 130 秒以上（至少过两次 60 秒的读取，抬头的新鲜度会重新变成“刚刚”），再打几个字，看完清空输入框，不发送。页面每次重画确认、每次读取之后都会对焦点该在的那个按钮再调一次 `focus()`，焦点离开确认之后才不再拉：页面里收到 `focusin` 落到确认的按钮之外；或者收到一次 `focusout`，它的 `relatedTarget` 是 `null`，离开的是确认里没有停用的“接管”或“取消”，而且这个按钮还在页面里（`plugin/codex/pane.html` 里 `focusout` 的处理）。焦点回到输入框时桌面应用派不派发这样的 `focusout`，看日志（8.7 再专门看一次）。再做一次转移失败的路径，这次用一个 Orphaned 的 Task：让 Task Source 读不到（`deck_occupy` 要现读 Task Source，读不到就不转移）。照 3.9 在 `/etc/hosts` 里加那一行、清 DNS 缓存：只挡 `api.github.com`，到模型服务的连接不动，对整台机器的影响同 3.9；转移会等到 `gh` 失败，有时间点别处。打开确认，点“接管”，趁转移进行中（两个按钮停用）点回 Codex 的输入框，等转移失败。#76 关闭评论里这条路径写的是“点页面空白处或回到 Codex 输入框”，这里只做回到输入框：点 Pane 空白处焦点还在页面里，回答不了页面会不会从输入框抢走焦点。失败之后，先在 Pane 里滚到底，截屏留下失败之后那几行日志（含 `hasFocus`），截屏时不点桌面应用。这几行可能不是紧跟着失败出现：转移失败后页面再读一次，这次读取排在读取链上；转移期间到了 60 秒一次的读取的话，它排在前面，也在等 `gh`（`deck_occupy` 现读时清了缓存，它读不到 15 秒内的缓存），所以失败之后那几行最多还要再等 3.9 量出的 `gh` 失败的时长，等它们出现了再截屏；再去终端删掉 `/etc/hosts` 里那一行，运行一次 3.9 那条清缓存的命令；然后用 ⌘Tab 回到桌面应用，不点窗口：点窗口回来焦点就变了，这一步要看的“回车落在哪里”就不成立。回来之后滚到底再读一次日志，看 `window focus` 那一行（和紧随的 `focusin`，有的话）。然后看 Codex 的输入框是不是空的：不空就把这条路径记为没做，不要点进去清空（点进输入框就改了这一步要看的焦点）；空的话不点任何地方，按一次回车。
- 应看到：**要核对**：打开确认后焦点在页面里；点回输入框、过了两次读取之后打的字仍进了输入框，焦点没有被拉回“取消”。焦点有没有被拉回页面，看日志里那一行的 `hasFocus` 和输入框里的字有没有进去，不看 `activeElement` 单独一项：焦点从页面回到宿主的输入框时，Chromium 不清掉页面里的 `document.activeElement`，它多半还是 `BUTTON 取消`，这时 `hasFocus` 是 `false`（按浏览器的行为推的，没在桌面应用里看过）。日志里写下点回输入框时有没有 `focusout`、它的 `relatedTarget`，“focusout 之后”那一行和之后每次读取那一行的 `activeElement`、`hasFocus`。点回输入框之后第一次读取那一行说明不了问题，至少看到第二次读取（点回输入框后 130 秒以上）：读取那一行 `hasFocus` 仍是 `false`、打的字进了输入框，就是没有被拉回；`hasFocus` 变成 `true`，就是页面的 `focus()` 把焦点拉回了页面。转移失败后提示留着，说明换成原因，结尾是“再点“接管”重试。”（`gh` 的报错认得出是连接问题时是“连不上 GitHub。检查网络后再点“接管”重试。”，认不出时是“`gh` 出错：<报错>。再点“接管”重试。”），页面把焦点放回这个“接管”（#76）；这时焦点是不是从 Codex 输入框被拉回了页面（看截屏里转移失败之后那几行的 `hasFocus`，同上）；⌘Tab 回到桌面应用之后焦点落在哪里（看回来之后 `window focus` 那一行、随后的 `focusin` 和它们的 `hasFocus`；没有 `window focus` 那一行的话，焦点多半没有回到页面），照实记下；回车落在哪里（#76 关闭评论“只能在真实桌面应用里核对的”）。落在“接管”上就是真的接管：`/etc/hosts` 已改回，转移成功后这个 Task 归丙，Execute Prompt 填进输入框，看完清空，不发送。落在输入框里，空的输入框按回车是发出一条空消息还是什么都不发，照实写下。来不及点回输入框的话，写下来，这条路径就记为没做。

**8.7 移除或停用有焦点的按钮时有没有 `focusout`**

- 做：用 6.2 换上的那份记日志的页面副本（改在专门检出上，这时还在），日志里每次 `focusout` 有两行：一行记 `event.target` 和 `event.relatedTarget`，紧接的“focusout 之后”一行记焦点落到的 `activeElement`。打开确认、焦点在“取消”上时，不动鼠标和键盘，等 60 秒一次的读取让它整表重画（点“刷新”不行：焦点先从“取消”移到“刷新”，`focusout` 在按钮被移除之前就发出了）。再对一个 Orphaned 的 Task 打开确认，点“接管”：页面在同一下里先停用它、再把确认整块移除重画（中间没有渲染，日志里也没有一行隔开），所以这里看的是“停用加移除”，分不出是哪一个引出的 `focusout`。这一下是真的接管，转移成功后 Occupancy 转给丙，Execute Prompt 填进输入框；看完日志清空输入框，不发送。最后对另一个 Orphaned 的 Task 再打开一次确认，焦点在“取消”上时点回 Codex 的输入框。
- 应看到：**要核对**：读取重画、按钮被移除时，和点“接管”、按钮停用加移除时，桌面应用各派没派发 `focusout`，派发了的话它的 `target` 和 `relatedTarget` 是什么（#76：页面里判断按钮还在不在、是否停用的两处防的就是这种情况，jsdom 不派发，没有测试守）。不拿“focusout 之后”和之后几行的 `activeElement` 判断移除那一刻焦点落在哪里：重画时页面已经排了一个微任务把焦点给新画出的按钮，它在 `focusout` 里 `setTimeout` 的那一行之前执行，读到的是页面重新放上去的焦点。焦点离开 iframe、回到输入框时有没有 `focusout`，`relatedTarget` 是不是 `null`（8.6 的焦点会不会被拉回就看这个）；那之后几行的 `hasFocus` 是不是 `false`，焦点在不在页面里看它，`activeElement` 可能还是“取消”，不能单凭它判断。

**8.8 读屏软件**

- 做：打开 macOS 的旁白（VoiceOver），在 Pane 上打开一个接管确认，等两三分钟不动。再让 Pane 上出现读取失败提示：照 3.9 在 `/etc/hosts` 里加那一行、清 DNS 缓存（只挡 `api.github.com`，到模型服务的连接不动，对整台机器的影响同 3.9），点“刷新”，等 `gh` 失败、提示出现，再等两三分钟。钩子未生效提示只在本机没记下钩子调用时显示，这时已经看不到，留到第 10 节重装之后、发消息之前做。做完关掉旁白，删掉 `/etc/hosts` 里那一行，再运行一次 3.9 那条清缓存的命令，点“刷新”：第 9、10 节都要连得上 GitHub。
- 应看到：**要核对**：读取失败时“任务”顶上是“读取 Task 失败”，下面是原因（`gh` 的报错认得出是连接问题时是“连不上 GitHub。检查网络后点“刷新”重试。”，认不出时是“`gh` 出错：<报错>。点“刷新”重试。”），抬头的新鲜度写“读取失败”；改回之后点“刷新”，提示消失（假宿主下测过）。接管确认带 `role="status"`，每次读取（60 秒一次）整张重建，旁白是否每次都把它重读一遍（#76）。另两种提示也带 `role="status"`，钩子提示每次读取只是显示或隐藏，读取失败提示每次换一遍文字；看旁白会不会因此重读。写下读了几次、读的是什么。

**8.9 结束 Claude Code 的 Session**
