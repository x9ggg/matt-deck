# Codex 侧以 MCP App 标签页为主路径

在 Codex 桌面应用（`ChatGPT.app`）里，面板做成 MCP App 的标签页（入口类型 `thread`）：每个会话一个实例，界面用带 `send:false` 的 `ui/message` 把文字预填进当前会话的输入框，由用户发送。首个里程碑只做 Claude Code。

## Considered Options

- **外部进程直接连 app-server 控制桌面端的会话**：不可行。桌面应用使用私有的 app-server，不连共享 daemon；通知只发给连在同一个 server 上并订阅了该会话的客户端；协议里也没有“当前聚焦的会话”。
- **内置浏览器加 WebMCP**：不够用。页面只能向 agent 提供工具，不能主动让聊天发出消息。
- **页面用 `ui/message` 直接向会话发消息**：不可用。消息能送达本会话，会话忙碌时宿主会排队，回合结束后送达。但宿主把页面的文字包成不可信输入交给 agent，agent 不照文字做，`$` 技能调用也不触发（实验一里 3 次都是）。
- **独立窗口加 `codex queue`**：没有做。它能一键发送，但要用户手选目标会话。预填只多按一次发送。

## Consequences

- 推荐请求和执行提示词都走预填。文字进输入框后不会自动发出，用户发送后它是普通用户消息，`$` 技能调用能触发。推荐请求见 ADR-0003。
- 页面感知不到会话是否忙碌，宿主在回合开始和结束时不通知页面。Codex 上面板不显示会话是否忙碌。
- Deck 在 Codex 上的安装和项目的首次配置是两步。安装每个用户做一次，用命令行的一条命令把 Deck 服务注册进用户全局的 `~/.codex/config.toml`，并明确告诉用户。首次配置要用 Deck 服务的工具，所以注册不能放在首次配置里。项目自己的 `.codex/config.toml` 不可用：桌面端的 MCP 服务目录按用户全局加载，目录一重新加载，项目级服务的标签页就被撤销。
- 全局注册使入口出现在这个用户的所有项目里。在未配置的项目里打开标签页，面板只提示此项目未配置，以及怎么配置。
- 注册之后要重启桌面应用，面板才打得开，只新建会话不够。会话能用哪些 MCP 服务在它被加载时定下，重启后会话恢复时会重新读配置。`config/mcpServer/reload` 可以显式重载，桌面端遇到 `unknown MCP server` 不会自动调它。没重启时标签页显示读取失败，这个界面由宿主绘制。安装说明写装完后重启桌面应用。
- 新会话发出第一条消息之前打不开面板，这时宿主的请求还不带会话 ID。
- Codex 上面板由用户手动打开标签页，自动出现的只是标签页菜单里的入口。官方规范只描述了手动打开。
- agent 调用入口工具时，宿主会在消息流里内嵌一个面板实例。这不算面板的一种位置，不专门支持，也不专门禁止，工具描述里写明它是给用户从标签页菜单打开的。把入口工具设成只对页面可见能否避免内嵌，没有测过。
- 只给页面用的工具带 `_meta.ui.visibility: ['app']`。Codex 照这个标记对模型隐藏工具：给模型的工具里没有它们，源码里模型调用不可见的工具会得到“不可用”。钩子调工具走宿主调用的路径，不看可见性，标了的工具钩子照样调得到。钩子的工具 `deck_prompt_submitted` 也标了，对模型不可见。
- Codex 按技能文件 frontmatter 的 `name` 认技能，`name` 为空才用文件夹名。它读用户目录和项目里的 `.agents/skills`、`.codex/skills`，不读 `~/.claude/skills`。两份不同的文件同名时，`$name` 一份都不注入；`$` 后面只认 `[A-Za-z0-9_:-]`。frontmatter 的 `disable-model-invocation` 不起作用；技能文件夹里有 `agents/openai.yaml`、写着 `policy.allow_implicit_invocation: false` 时，技能才不进模型看得到的列表，用户发 `$name` 照常注入。扫几层目录、链接和读不了的条目怎么算，见 #95 的 Agent Brief；指到技能文件本身的链接 Codex 不跟，只跟指到目录的（`codex-rs/exec-server/src/local_file_system.rs` 的 `sync_walk`；#95 验收时用 `codex-cli 0.172.0` 实测过：`SKILL.md` 本身是文件链接的技能不列出，发 `$name` 也不注入，经目录链接的照常注入）。
- 每个会话有自己的服务进程，工作目录是会话的目录，每个标签页是一个独立的页面实例。页面可以经宿主调用服务的工具，会话空闲和忙碌时都行。宿主还会起一些几秒就结束的服务进程，它们收不到工具调用，所以服务启动时不做任何有后果的事。
- Codex 上会话标识由 Deck 服务从每次工具调用的 `_meta.threadId` 读取，页面调用、agent 调用和钩子调用都带。页面自己拿不到会话标识。
- 占用由 `UserPromptSubmit` 钩子登记：安装时在 `~/.codex/hooks.json` 里加一个钩子，它直接调 Deck 服务的工具并带上提示词原文，服务从中认出 `$implement` 的调用。让 agent 自己调工具登记被否决，因为手敲的调用覆盖不到，还要靠 agent 照办。
- 钩子要用户信任一次才运行，桌面应用不提示，要在 Codex 的终端界面里做。信任按钩子在文件里的位置和内容的哈希记录，所以安装写进去的钩子内容要保持不变，否则升级后要重新信任。安装命令的最后一步告诉用户去信任。Deck 不替用户写信任记录，那等于绕过 Codex 的安全审查。Deck 记下最近一次收到钩子调用的时间（未配置的项目里收到的调用只记在这个 Session 的服务进程里，不写本机状态），安装后从没收到过时，面板顶部提示钩子未生效、开始执行不会登记占用，并写明做法。
- 心跳由服务进程自己写，从收到第一次带会话标识的调用开始。宿主用 `SIGTERM` 结束服务进程，服务在这时写结束记录。
- Codex 上面板读不到回答文本，`deck_recommend` 是唯一的结果回传通道（见 ADR-0003）。
- 最初的事实调研于 2026-11-11：本机 `codex-cli` 为 0.165.0，桌面应用自带 0.167.0-alpha；源码依据来自 `openai/codex` 的 main 分支。
- 实验一做于 2026-11-21，桌面版 26.1117.41037，自带 `codex-cli 0.171.0-alpha.13`。上面关于直接发送、预填、忙碌、注册、重启和内嵌的结论都来自这次实验，见[实验一记录及探针](../research/probes/adr6-thread-tab/README.md)。同日补查的事实对的是 `openai/codex` 的 `rust-v0.171.0-alpha.13`、`openai/mcp-extensions` 的 `docs/spec.md` 和 MCP Apps 规范 2026-01-26。
- 会话标识、钩子和服务进程的结论来自 2026-11-22 的第二个探针，版本同上，见[钩子和会话标识的探针记录](../research/probes/codex-hooks/README.md)。
- 工具可见性和技能认法的结论来自 2026-11-26 分诊 #97、#95 和 #87 时的实测：本机 `codex-cli 0.172.0`，临时的 `HOME` 和 `CODEX_HOME`，模型端是本机的假服务；源码对的是 `openai/codex` 的 `rust-v0.172.0` 和 main 的 `af71942309`。未在桌面应用里核对，桌面应用自带的是 `0.171.0-alpha.13`。
